# Runway specification

Version: 0.1.0 · Status: experimental · Platform: macOS-first

## Purpose

Provide one local dashboard for a person's Claude subscription accounts and
official Claude Code sessions, without proxying inference. Make account selection,
quota freshness, credential health and session ownership visible.

## Scope and non-goals

The manager and controlled CLI processes run on the same Mac. Project folders
may be anywhere accessible to the user. Multiple managed sessions share one
account selection; per-session independent routing is not implemented.

Not in scope: reselling access, pooling other people's credentials as a service,
remote hosting, bypassing provider limits, a replacement Claude client, automatic
adoption of arbitrary running sessions, or guaranteed provider compatibility.
Source availability and a no-proxy design do not establish provider approval.

## User journeys

### Connect an account

1. Enter an account label; labels are not verified email identities.
2. Launch the official `claude setup-token` flow in an isolated enrollment
   directory, or paste a setup token generated by official Claude Code.
3. The account owner completes browser authentication when required.
4. Store the token in the local encrypted vault; never return it in API snapshots.
5. Attempt a usage lookup; show unknown/unavailable quota when lookup is unsupported.

Repeat for additional accounts; there is no two-account product cap. Token
fingerprints reject duplicate credentials, not different tokens for the same identity.
Only one browser enrollment job runs at a time. API keys and cloud authentication
are not accepted. Reconnect replaces an account's token while retaining its ID.

An explicit Test connection action sends one tiny Haiku request through official
Claude using an isolated temporary file-based configuration, no tools, safe mode,
and no session persistence. It has a 45-second timeout, removes its temporary
configuration afterward, and never switches managed sessions. The UI asks for
confirmation because this consumes quota. A successful marker establishes request
access, not account identity, quota availability or future reliability. Only the
classified result and timestamp are stored; raw CLI output is not exposed.

### Start or inspect a session

Choose an account and an existing absolute project directory. Launch official
Claude in a managed tmux session, preserving native trust and permission prompts.
View/interact in the dashboard, or copy a tmux attach command for a local terminal.
Stopping a managed session retains its conversation; archiving removes its list entry.

Discover other native Claude processes belonging to the same OS user every 15
seconds. Show PID and terminal identity, without reading arguments, environment,
credentials or conversations. Exclude managed descendants and helper processes.
Discovery is best-effort and read-only, not a historical session browser or adoption flow.

### Track usage and credential health

- Poll usage every 90 seconds, respecting per-account retry backoff.
- Track all registered accounts, including those disabled for switching.
- Accept matching native status-line quota telemetry after managed responses.
- Distinguish usage observation age from dashboard connection freshness.
- Show unknown quota as unknown, not zero. Preserve cached observations on failure.
- Show known expiration times and warn within 24 hours; otherwise show unknown expiry.
- HTTP 401 or known expiration requires reconnecting. Polling is not token renewal.

The direct usage endpoint is undocumented and may throttle, reject setup tokens,
or change. Endpoint HTTP 429 does not prove the account's inference quota is exhausted.

### Select accounts

Manual switching requires an enabled account and waits until managed sessions
are not producing responses. The credential file is atomically replaced; the CLI
processes and conversation IDs remain unchanged.

Automatic selection is opt-in, with default threshold 95%. A candidate must have:

- Enabled status, verified authentication and no known imminent expiration.
- A quota observation less than five minutes old, including the five-hour window.
- Finite values for every returned window, all below the selected threshold.
- No active cooldown, and an ID different from the selected account.

Choose the candidate with the lowest maximum window utilization, breaking ties by
name. The monitor ticks every three seconds and waits at least 60 seconds between
switches. Working managed sessions defer the shared switch.

Synthetic CLI limit errors can trigger failover. After switching, allow at least
35 seconds before sending one continuation to the failed session, only when its
prompt is empty and idle. Do not overwrite user drafts or interrupt working tasks.
The current limit classifier can mark the five-hour window full without knowing
the exact exhausted window; precise error attribution is a known improvement area.
Real provider limit recovery remains unverified.

## Architecture

```text
Browser dashboard ── authenticated localhost API ── Node manager
                                                    ├─ encrypted local vault
                                                    ├─ direct usage lookup
                                                    └─ shared credential file
                                                         ↓
                                                 official Claude / tmux
                                                         ↓
                                                    Anthropic
```

`lib/core.mjs`: selection, environment isolation, encryption and atomic storage.
`lib/manager.mjs`: enrollment, account lifecycle, usage and session supervision.
`lib/discovery.mjs`: read-only native process discovery.
`lib/activity.mjs` and `lib/statusline.mjs`: activity and quota observations.
`server.mjs`: local authenticated API and static assets.
`public/`: framework-free dashboard. `cli.mjs`: open/status/launch commands.

The local HTTP server binds only `127.0.0.1`, validates Host/Origin, and requires a
random bearer key for API calls. It is not an inference proxy. The browser access
key is passed in a fragment, moved into session storage, and removed from the URL.

State includes account metadata, encrypted vault entries, a local vault key,
managed Claude config/transcripts, activity, telemetry and service logs. The vault
key and active plaintext credential are mode 0600; the state root is mode 0700.
Same-user malware is outside this protection boundary. See SECURITY.md.

## Lifecycle and compatibility

The dashboard can run in the foreground or as a per-user LaunchAgent. Stopping
the manager leaves tmux sessions alive but stops automatic monitoring. Sleep
pauses monitoring. Existing default Claude configuration is not intentionally
rewritten. Project configuration may override required hooks.

No refresh-token synchronization is implemented. Long-lived setup tokens can
still expire or be revoked. File-based live reload was demonstrated with Claude
Code 2.1.268; future versions or matching Keychain entries may change behavior.
The manager never reads/writes Keychain; native enrollment may use it.

## Acceptance and verification

Implemented and covered by isolated tests: selection guards, vault integrity,
busy-session deferral, synthetic-error switching, disabled-account tracking and
process filtering. Browser tests cover six fixture accounts, mobile layout,
enrollment UI, managed terminal visibility and API access rejection.

Observed live: account A → invalid token → account B, with the same interactive
process and retained context; dashboard-driven switching between two saved tokens.

Required before claiming production readiness:

- Complete new-account browser enrollment end to end.
- Verify real quota exhaustion, switching, continuation and billing identity.
- Exercise long-term expiry/revocation and reconnect behavior.
- Validate recovery after sleep, manager restart and CLI updates.
- Review hooks, stale activity, Keychain conflicts and multi-session races.
- Assess provider terms and authentication compatibility independently.

See VERIFICATION.md for evidence. Tests must not silently spend quota or modify
unrelated work sessions. Real inference tests require explicit opt-in.
